Required Environment Variables (Vercel → Settings → Environment Variables)

VariableRequired?What it does
APP_SECRET Required Long random string (64+ chars). Encrypts Nick's authenticator secret and keys all recovery codes & unlock tokens. Use the same value in Preview and Production. Never use the Supabase key — rotating Supabase after a breach would lock Nick out of 2FA permanently.
SUPABASE_SERVICE_ROLE_KEY Required From Supabase → Project → Settings → API. The service-role (secret) key, not the anon key.
RESEND_API_KEY Required From resend.com. Sends login codes, payment links, and tracking links to clients. Without it, emails are silently skipped in production.
STRIPE_SECRET_KEY Required From Stripe → Developers → API keys. Use the test key (sk_test_…) until you're ready to take real payments.
STRIPE_WEBHOOK_SECRET Needed for payments From Stripe → Webhooks → your endpoint. Required to automatically mark orders as paid when Stripe confirms the payment. Without it, Nick has to mark orders paid manually.
CRON_SECRET Recommended Any long random string. Protects the daily cleanup endpoint from being triggered by anyone. Set it in Vercel; Vercel Cron passes it automatically.
SUPABASE_URL Auto-set Already hard-coded to wlbmtcrgftermdtwnbgb.supabase.co. Only needed if the project changes.
ADMIN_EMAILS Auto-set Defaults to nicksprocessservices@outlook.com. Set this to change which email addresses can log in to the dashboard.

1 · Admin Dashboard Login

Two-step sign-in, session cap, security alerts
  • 1Go to /admin.html — you'll see the email sign-in screen.
  • 2Enter nicksprocessservices@outlook.com and click "Send Code." Nick gets an 8-digit code by email (Resend must be configured).
  • 3Enter the code. First login: signs in. After 2FA is set up, a second prompt appears for the authenticator code.
  • 4Check Nick's email — a security alert arrives for every sign-in. If Nick didn't do it, the alert is his warning.
  • 5Try wrong codes 5 times — all codes are burned, Nick gets a lockout alert. Rate limit resets after 15 minutes.

2 · Set Up Authenticator App (2FA)

Encrypted TOTP, recovery codes, replay prevention
  • 1Sign in to the dashboard and go to Settings → Two-Step Sign-in.
  • 2Scan the QR code with Google Authenticator, Authy, or any TOTP app on your phone.
  • 3Enter the 6-digit code from the app to confirm. Your next sign-in will require both the email code AND the app code.
  • 4Generate recovery codes (Settings → Recovery Codes) and print or save them. If you lose your phone, one of these 8-character codes gets you back in.
  • 5Verify: Sign out, sign back in — you should now see a second prompt asking for your authenticator code.
Open Dashboard → Settings

Public form → dashboard review → tracking link

4 · Legal Hold on a Served Order

DB-enforced freeze, tamper-evident timeline, unlock requires fresh code
  • 1In the dashboard, open any "Served" order and click "Place Legal Hold." The order is now frozen at the database level — not just in the app.
  • 2Try to delete or edit the order — the dashboard refuses, and the database itself blocks it too.
  • 3Billing still works on held orders: send a payment link, record a payment — the order stays "Served" but records the money.
  • 4To unlock (e.g. court case resolved): go to the order → Unlock Hold. With 2FA on, you need your authenticator code. Every unlock is logged permanently.
  • 5Nick gets a security alert email any time a hold is unlocked, even if he did it himself.
Open Dashboard

5 · Client 2-Step Document Lock

Tracking page PIN or emailed code, 12-hr signed unlock token
  • 1On a client's tracking page, click "Enable 2-Step Protection." Court documents, address, and name are now blurred.
  • 2Refresh the page. The client must enter a code to see anything. They click "Send Code" → get a 6-digit code by email → enter it to unlock for 12 hours.
  • 3Optionally set a Security PIN (6 digits): the client's chosen PIN unlocks the page instead of requesting an email code every time.
  • 4Rotate the tracking link (Settings on the tracking page) if the client suspects their link was shared. Old link stops working; new link is emailed.
  • 5Try 5 wrong codes — the client is locked out for 15 minutes and must request a fresh code.
Open Tracking Page

6 · Tamper-Evident Chain of Custody

Hash-chained timeline, sealed at database write, verify anytime
  • 1In the dashboard, open a served order and click "Chain of Custody." A printable PDF shows the full timeline.
  • 2Every event in the timeline (status change, payment, note, file upload) is hashed and chained — changing any entry breaks every subsequent hash.
  • 3When proofs are uploaded, the client is emailed the SHA-256 fingerprint of each file plus the chain seal. This is an out-of-band copy that survives a database breach.
  • 4The chain is verified live each time you view the seal — any forgery shows "chain integrity failed."
  • 5Useful in court: the emailed seal + file fingerprints prove the proof documents existed at that date and were not altered afterward.
Open Dashboard
📎

7 · Secure File Uploads

Magic bytes, macro scan, polyglot detection, SHA-256 fingerprint
  • 1On any order's tracking page, try uploading a PDF, JPG, or DOCX. The server checks the actual file bytes — not just the filename.
  • 2Try renaming a .jpg as .pdf — the upload is rejected because the binary signature doesn't match.
  • 3DOCX files are scanned internally — any macro, script injection, or embedded executable triggers rejection.
  • 4Each uploaded file gets a SHA-256 fingerprint stored in the database. Nick can verify a file hasn't been swapped after upload.
  • 5Maximum 25 files per order. Files on orders under legal hold cannot be deleted.

12 · Security Hardening

Emailed step-up, whole-file PDF scan, server-side photo cleaning
  • 1Sensitive actions confirm it's really Nick. With the authenticator app off, deleting a request, unlocking legal hold, new recovery codes, authenticator setup and passkey removal ask for an 8-digit code emailed to him (demo code 12345678). It then covers that device for 5 minutes.
  • 2PDF uploads are scanned end to end for code-running, program-launching, embedded-file and form-submit features, including names disguised with #xx escapes, and for hidden HTML/script.
  • 3Photos are cleaned on the server too. GPS and camera data are removed from JPEG, PNG, WebP and HEIC files even if someone uploads straight to storage, and the SHA-256 fingerprint is taken of the cleaned file.
  • 4"Secure your dashboard" walks Nick through the authenticator app, 8 recovery codes and Face ID; an amber banner appears when 3 or fewer recovery codes are left.

Security Summary — What's Protected

🏗️

Infrastructure

  • ✅
    All API keys derived via HKDF-SHA256One root secret → separate keys per purpose. No key reuse.
  • ✅
    TOTP secrets encrypted AES-256-GCMStored as v1.<iv>.<tag>.<ct> — unreadable without APP_SECRET.
  • ✅
    scrypt PIN hashing (N=16384)Memory-hard. A 6-digit PIN cannot be cracked in reasonable time without APP_SECRET.
  • ✅
    Session tokens stored as SHA-256A full DB dump gives attackers nothing usable.
  • ✅
    Constant-time comparisons everywherePrevents timing side-channel attacks on codes and tokens.
  • ✅
    Atomic TOTP replay preventionEach 30-second code can be used exactly once.
⚖️

Legal Protection

  • ✅
    Legal hold enforced at DB levelNo API call, bug, or mistake can delete a held order.
  • ✅
    Hash-chained, append-only timelineEvery event is SHA-256 chained. Forgery is detectable. Entries cannot be deleted or edited.
  • ✅
    Immutable audit logEvery admin action is permanently logged. UPDATE/DELETE on the log are blocked by DB trigger.
  • ✅
    SHA-256 file fingerprintsEach uploaded proof file is fingerprinted. Emailed to client out-of-band at proof completion.
  • ✅
    Billing works on held ordersSending a payment link or recording payment doesn't unlock or alter the hold.
  • ✅
    Every download loggedNick's document accesses appear in the audit log by order and filename.

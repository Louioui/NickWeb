**8. The request form.** The old single long form is now a three-step wizard: First, "You & your case": contact details, case number, court, the client's own reference number, deadline, and document upload. Second, "Person to serve": name, document type, street, unit, city, ZIP, gate or access notes, and a physical description. Third, "Add-ons & review": add-ons, instructions, a live recap, the terms checkbox, and a hidden honeypot field named `website` that only bots fill in. The right-hand order summary and plan switcher are unchanged. Each step checks its fields before moving on. Invalid fields are announced to screen readers with `aria-invalid`, and the step indicator is made of real buttons, so it works with a keyboard. Submitting runs three stages: First, `POST /api/request` with `step: 'create'` saves the order and returns one signed upload URL per file. Second, the browser uploads each file straight to private storage. This avoids Vercel's roughly 4.5 MB limit on request bodies. Third, `step: 'finish'` confirms the uploads and sends one email to the client and one to Nick. A submitting flag blocks double submits; a stress test had once produced two orders from one rapid double submit. The finish step is retried once, because it's the step that sends the confirmation emails. The confirmation modal shows the `NP-######` reference number and a link to the private tracking page.

**9. The API endpoints.** `api/request.mjs` creates orders and finishes their uploads. `api/track.mjs` serves the client's tracking page. Every call is a POST with the token in the body: `view`, `download`, `confirm-payment`, `respond` for "Action required", and `respond-finish`. `api/lookup.mjs` handles "Track existing serve". It takes a reference number and email, always gives the same answer, and emails the private link only if both match, so it can't be used to discover which codes or emails exist. `api/admin.mjs` is Nick's dashboard API: `send-code`, `verify-code`, `me` and `logout`; `list` and `get`; `update`, with kinds `status`, `attempt`, `note` and `action`; `payment-link`, `proof-upload`, `proof-finish` and `file-url`; `export` and `delete`, added for privacy requests. `api/stripe-webhook.mjs` checks Stripe's signature against the raw request body and marks orders paid on `checkout.session.completed` and `checkout.session.async_payment_succeeded`. `api/keepalive.mjs` runs daily from `vercel.json`'s cron (`0 15 * * *`). It runs a real database query so the free Supabase project doesn't pause after seven idle days, deletes expired login codes and sessions, and checks uploads left unconfirmed for more than a day. Files that really reached storage are kept and marked uploaded, empty records are removed, and it handles at most 100 a run. Each endpoint goes through `handle()`: expected errors come back as clean JSON messages, and anything unexpected is logged and hidden behind a generic message.

**10. The database.** The first migration, `supabase/migrations/20261029031715_phase1_orders_tracking.sql`, defines `orders`, which holds the human reference `code` and the 192-bit `track_token`; `status`, limited to `received`, `action_required`, `awaiting_payment`, `paid`, `accepted`, `attempting`, `served`, `closed` and `cancelled`; client fields, case fields and the recipient's details; `tier`, `addons` and the estimate in cents; `amount_due_cents`, `stripe_session_id`, `payment_url` and `paid_at`; `action_note` and `served_at`. `order_events`, the timeline, with a `kind`, a title, details, and `client_visible`. `order_files`, with a `kind` of `client_document`, `proof` or `action_upload`, the storage path, the size, and an `uploaded` flag. `admin_codes` and `admin_sessions`. `rate_limits`, with the atomic `hit_rate_limit(bucket, window)` function, which counts hits in one upsert and clears itself. Four later migrations harden it: `atomic_admin_code_check` and `admin_code_hourly_guess_cap` add `use_admin_code(email, hash)`, which checks a login code in one locked step (at most 5 tries per code and 25 wrong guesses per hour per email), and `admin_codes_last_hour(email)`, which counts the codes sent in the last hour. `case_files_no_legacy_doc` stops the storage bucket accepting old `.doc` files. `deny_public_roles_defense_in_depth` takes every privilege away from the public `anon` and `authenticated` roles, now and for future tables, and adds a restrictive deny-all rule to every table. All five migrations are applied to the live database and saved in the repository. Any future schema change must be a new migration file applied with the Supabase tools, never a hand edit in the dashboard.

**11. Storage and uploads.** Files live in the private Supabase Storage bucket `case-files`, which takes at most 25 MB per file and only PDF, DOCX, JPEG, PNG, HEIC, HEIF and WebP. Each upload is stored at `orders/<orderId>/<client|proof|action>/<random>-<safe name>`. The server creates the upload links (`prepareUploads`), and a file only counts once the server confirms it actually exists in storage (`confirmUploads`). Downloads use signed URLs that last five minutes and are sent as attachments, so a file can't run as a web page on our domain. File type comes only from the extension, never from what the browser claims, so a file named `notes.html` but labelled as a PDF is refused. Old `.doc` files are refused because they can carry macro viruses; `.docx` is fine. The browser runs the same checks first, so clients get a clear message straight away. There is no malware scanning yet; paragraph 46 explains the trade-off. Supabase encrypts stored files at rest as part of its platform, but the site doesn't add its own file-level encryption. Don't advertise "AES-256 vault" or similar claims until you've confirmed exactly what Supabase provides and the user and Nick agree to the wording.

**12. The tracking page and the token design.** A client's private link looks like `https://www.nicksprocessservices.dev/track.html#t=<token>`. The token is 24 random bytes (192 bits) in base64url, and it is the only key to the page. Holding the reference number alone never shows anything. The token sits after the `#` on purpose: browsers never send that part to a server, so it can't end up in Vercel's request logs or in the Referer header sent to other sites. The page then fetches its data by POST with the token in the body. Older `?t=` links still work and are moved behind the `#` the moment the page loads. A `hashchange` listener reloads the page when another order's link opens in the same tab; a test caught the wrong order being shown. The page shows: the status, with a four-stage progress bar (Received, Payment, Attempting service, Served); the case details; a gold "Amount due" card with a Pay button when Nick has sent a payment link; Nick's question and a reply form with uploads when the status is "Action required"; the proof of service and the client's documents to download; a timeline that shows only the entries marked visible to the client, so Nick's internal notes never appear. The page sends `Referrer-Policy: no-referrer`, `Cache-Control: no-store` and `X-Robots-Tag: noindex`.

**15. How Nick logs in today.** Nick enters his email, and if it's in `ADMIN_EMAILS` (default nicksprocessservices@outlook.com) the server emails an 8-digit code. The code is stored as `sha256(email:code)`, expires after 10 minutes, allows 5 attempts, and is checked atomically by `use_admin_code`. At most 10 codes are sent per hour, and the database caps wrong guesses at 25 per hour across all of an address's codes. Any other address gets the same "a code is on its way" answer, so the allowed address isn't revealed. A correct code creates a 256-bit session token, stored only as a hash in `admin_sessions`. It's sent as the cookie `nps_admin`: HttpOnly, Secure everywhere except localhost, SameSite=Strict, scoped to `/api/admin`, and valid for 14 days. This is one factor: whoever controls Nick's Outlook inbox controls the dashboard. That's why paragraphs 40 to 44 plan passkeys and recovery codes, and why two-step sign-in on Nick's Outlook account matters even before then. Locally, in mock mode, the login code is always `12345678` and only works on the developer's machine.

**20. Database security in detail.** The design rule is that the browser never talks to the database. Only the server functions do, using the `service_role` key, which bypasses row-level security by design and lives only in Vercel environment variables (and in `.env.local` for local testing). Every table has row-level security on. Every privilege has been taken away from the public `anon` and `authenticated` roles, and every table has a restrictive `deny public roles` rule. Because restrictive rules are combined with AND, even a permissive rule added by mistake later would not let those roles in. Security-definer functions are revoked from public roles, and new functions default to no public execute permission. The storage bucket is private and refuses outside uploads. When you add a table, enable row-level security, revoke public access, add the same restrictive rule in the same migration, then run Supabase's security advisor. The user should also turn off "Allow new users to sign up" in Supabase Authentication. The site doesn't use Supabase Auth, and while the public key lets anyone create users, they can't see anything.

**21. Application-layer protections.** In the server code: **Only same-site JSON is accepted.** `readJson` refuses anything that isn't `application/json` (415) and anything whose Origin header doesn't exactly match the request's own origin (403). This blocks requests sent from other websites, adding a second lock alongside the SameSite cookie. **Body size.** Request bodies are capped at 64 KB. **IDs.** IDs from the browser must be real UUIDs (`uuid`, `uuidList`) before they reach a query. **Text.** Text fields are trimmed, whitespace is collapsed, and lengths are capped to match the database. **Prices.** Only the defined tier and add-on keys count (`Object.hasOwn`). **Rate limits** are counted in the database per IP, which Vercel sets itself so it can't be faked: 8 requests an hour; 6 lookups per 15 minutes; 5 login-code emails and 10 code checks per 15 minutes; 120 tracking calls per 10 minutes. **The cleanup job.** It needs `CRON_SECRET` once that's set; until then it's throttled to 4 runs an hour. **Email links** always use the real domain in production (`siteOrigin`). **Errors.** Malformed cookies count as logged out instead of causing a server error, and visitors never see configuration errors.

**22. Hosting protections.** In `vercel.json`: **Source files aren't served.** Redirects send requests for these paths back to `/`: `/api/_lib/*`, `/api/*.mjs`, `/scripts/*`, `/src/*`, `/supabase/*` and `/docs/*`; `/build/*` and `/node_modules/*`; `package.json`, `vercel.json`, `.gitignore` and `.env*`. A probe found that the live site served files like `/scripts/inline-css.js`, so this matters. **Headers on every page:** `X-Content-Type-Options: nosniff`, a referrer policy, a `Permissions-Policy` that turns off camera, microphone and location, and a Content-Security-Policy. The policy allows only the site's own scripts and styles, plus OpenStreetMap map images and the Supabase upload host, and blocks other sites from framing the pages. **The tracking page and dashboard** get an even stricter policy. **API calls** are capped at 10 seconds (`functions` → `maxDuration`). **Fonts and libraries** are cached for a year. Font Awesome and Leaflet are self-hosted under `assets/vendor/` with their licenses, so loading the site contacts no third-party CDN. HTTPS is enforced by Vercel's default HSTS header. On 2026-10-29 the live Vercel firewall gained the custom rule "Rate limit /api/ requests": 60 requests per 60 seconds per IP on paths starting with `/api/`, and IPs over the limit are denied for 15 minutes. The user accepted Vercel's price of $0.50 per million requests it lets through; blocked requests are free. Vercel's built-in DDoS protection had already blocked 814 requests in the previous day, so the site is being probed.

**37. The installable app (PWA): what it is.** A Progressive Web App is a website that the browser can install like an app. It gets a home-screen or dock icon, opens in its own window without the address bar, and can work partly offline and, in some cases, show notifications. That's exactly what Nick's notes describe ("Install it directly onto his phone's home screen from the browser"), without the App Store or Play Store. The recommendation is to make **Nick's dashboard** the installable app: start URL `/admin.html`, named "Nick's Dashboard" or "NPS Dashboard". Only `admin.html` links to the app manifest, so clients on the homepage never see an install prompt and the front page doesn't change. Installing works on iPhone and iPad (Safari → Share → Add to Home Screen), Android (Chrome's install prompt or menu → Install app), and desktop (Chrome or Edge's install icon in the address bar, or Safari on macOS Sonoma and later → File → Add to Dock). Write Nick a short illustrated note per device. He shouldn't need to understand what a PWA is.

**38. The installable app: technical design.** **The manifest.** Add `manifest.webmanifest` with `name`, `short_name`, `start_url: "/admin.html"`, `scope: "/"`, `display: "standalone"`, `theme_color` and `background_color` (the site's greens, `#0d422e` and `#082b1e`), and `icons` at 192 and 512 pixels plus 512-pixel maskable icons made from the scales-of-justice mark. Also add an `apple-touch-icon` at 180 pixels and `<meta name="apple-mobile-web-app-capable">` in `admin.html`'s head. **The service worker.** Add `sw.js` at the site root so its scope covers `/admin.html`, and register it only from `admin.html`. It caches the app's shell (`admin.html`, `assets/js/nps.js`, the self-hosted fonts and icons) so the dashboard opens instantly and shows a friendly "you're offline" screen with no signal. **It never caches `/api/*` responses, signed file URLs or anything with client data.** That traffic stays network-only, so private case data never sits in a cache on a lost phone. Bump a version constant on every deploy and delete old caches in the `activate` step. **The CSP** already allows workers and manifests from `self` through `default-src 'self'`. Confirm with a deploy check, and add `manifest-src 'self'` and `worker-src 'self'` explicitly if needed. **Hosting.** Serve the manifest as `application/manifest+json`, and add `sw.js` and the manifest to the self-hosted caching rules carefully. The service worker itself must **not** be cached for a long time (`Cache-Control: no-cache`), or updates won't arrive. **Testing.** Check with Chrome DevTools' Application panel and Lighthouse's PWA checks, then install on a real iPhone and Android phone from the Preview URL.

**39. The installable app: later possibilities and their risks.** **Push notifications.** Once installed, the dashboard could show a notification on Nick's phone when a new request or client reply arrives. This works on Android and desktop, and on iOS 16.4+ for home-screen apps. It needs VAPID keys, a `push_subscriptions` table, the `web-push` library on the server, and a permission prompt Nick accepts. It complements email and doesn't replace it. **The "Offline Attempt Logger"** from Nick's notes is harder than it looks. Storing attempts and photos in IndexedDB on the phone and syncing them later means case data sits on the device. That needs the phone locked with a passcode, encryption with a key that isn't stored next to the data, a way to resolve conflicts, and an exact record of which timestamps are "logged offline" versus "synced". Otherwise the record could be challenged in court. **Camera and GPS capture** need `Permissions-Policy` changes: today camera and location are turned off on every page. They'd be re-enabled only for the dashboard, with a clear on-screen indicator. Treat all three as later phases. The first PWA release should be only installability plus the offline shell.

**40. Why Nick needs two-factor sign-in.** Today a single factor (access to Nick's Outlook inbox) opens a dashboard holding every client's court documents, home addresses of people being served, and payment links. Email accounts are the most phished accounts there are, and a stolen inbox session gives the attacker the next login code too. Two-factor authentication requires a second, independent proof. The best one available today is a **passkey**: a WebAuthn credential stored in the phone or laptop's secure hardware, synced through iCloud Keychain or Google Password Manager, and unlocked with Face ID, Touch ID or the device PIN. Passkeys resist phishing by design: the browser only releases a signature to the real `nicksprocessservices.dev` domain, so a look-alike site gets nothing. **Recovery codes**, one-time codes Nick saves offline, cover the case where he loses or replaces his device. The target state: a passkey alone logs Nick in, because it is something he has *and* something he is or knows; if he has no passkey with him, he needs the email code **plus** a recovery code; adding or removing a passkey always requires a recent strong check.

**41. Passkeys: data model and libraries.** **New tables.** Add these in a new migration, following paragraph 20's row-level security rules: `admin_passkeys`: `id`, `email`, `credential_id` (base64url, unique), `public_key` (bytea), `sign_count` (bigint), `transports` (text array), `device_label`, `created_at` and `last_used_at`; `admin_webauthn_challenges`: `id`, `email`, `challenge`, `purpose` (`register` or `login`), `expires_at` (5 minutes) and `used`; `admin_recovery_codes`: `id`, `email`, `code_hash`, `created_at` and `used_at`; `admin_audit`: `id`, `email`, `action`, `ip`, `user_agent`, `created_at` and `detail`. **The server library.** Use `@simplewebauthn/server` (a well-maintained, MIT-licensed npm package; pin an exact version and run `npm audit`) in the Vercel functions. **The browser library.** Self-host `@simplewebauthn/browser`'s built file in `assets/vendor/` like Font Awesome, because the CSP blocks CDNs. Alternatively, call `navigator.credentials.create`/`get` directly with careful base64url handling. **The domain (relying-party ID).** Configure it through an environment variable: `RP_ID=nicksprocessservices.dev` and `RP_ORIGIN=https://www.nicksprocessservices.dev` in Production. A passkey made for the bare domain also works on `www.`. **Previews.** Preview deployments on `*.vercel.app` can't use production passkeys, so Previews need their own values. Otherwise passkey testing has to happen on a dedicated preview domain.

**42. Passkeys: how registration and login work.** **Registering** a passkey happens only inside an already logged-in session that has *just* been checked strongly, within the last 5 minutes. On first setup that's the email code; once anything is enrolled, it's an existing passkey or email code plus a recovery code. First, the server makes registration options with `generateRegistrationOptions`. They require user verification and a resident key, exclude credentials already registered, and are saved as a single-use challenge. Second, the browser runs `startRegistration`. Third, the server checks the result with `verifyRegistrationResponse` against the stored challenge, expected origin and domain, then stores the credential and marks the challenge used. Fourth, nick gets an email: "A new passkey was added to your dashboard from <device/browser>. If this wasn't you, reply immediately." The event is written to `admin_audit`. **Logging in** uses `generateAuthenticationOptions` (user verification required, with discoverable credentials so Nick doesn't even type his email) and `startAuthentication`. The server verifies with `verifyAuthenticationResponse`, checking the challenge, origin, domain and signature. If the authenticator reports a non-zero `sign_count` lower than the stored one, refuse and alert. Synced passkeys often report 0, which is allowed. Update `sign_count` and `last_used_at`, then create the same `nps_admin` session as today, recording in the session that a passkey was used. **Rate-limit** every passkey endpoint like the code endpoints, and accept a challenge only once.

**43. Recovery codes.** When Nick enrolls his first passkey, the server generates **10 recovery codes**. Each is 10 characters from a 32-character alphabet without confusable letters, grouped `XXXXX-XXXXX` for readability. That's about 50 bits of randomness each, from `crypto.randomBytes`. They are shown **once**, with "Download as a text file" and "Print" buttons, and a checkbox "I saved these somewhere safe" that must be ticked before continuing. Advise Nick to print them and keep them with his business papers, or store them in his password manager, not in his email. The database stores only a hash of each code. SHA-256 is acceptable because the codes are high-entropy; a slow hash like scrypt is optional. Each code works once, through a single atomic `update … where used_at is null` returning the row, so the same code can't succeed twice in parallel. Generating a new set invalidates all old ones. Using a code sends Nick an email alert with the number of codes left and writes an audit entry. When three or fewer are left, the dashboard shows a banner prompting him to generate a new set.

**44. Login policy, sessions and keeping it easy for Nick.** **Before he has a passkey**, the login is today's email code, and right after logging in the dashboard shows a one-time, skippable setup card: "Add Face ID / Touch ID login (recommended)". **Once he has a passkey**, email-code-only login is turned off. The login screen offers "Sign in with passkey" first, and "Use email code + recovery code" behind a small "Can't use your passkey?" link. **Sensitive actions require a fresh check within the last 5 minutes:** adding or removing passkeys and generating recovery codes; deleting a request permanently; changing where emails go. With a passkey that's one Face ID tap, so it's barely noticeable. **Sessions.** Keep the 14-day session only for devices that logged in with a passkey, cut sessions created by email code plus recovery code to 24 hours, and add an idle timeout of about 12 hours.
